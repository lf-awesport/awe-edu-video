# Approval and change-control contract / Contratto approvazioni e change control

**Candidate normative annex. Effective status inherits the parent specification (`in-review`); it becomes implementation authority only when that parent is approved.** Applicable requirement IDs: **APPROVAL-001–APPROVAL-004, RIGHTS-003, RELEASE-005**. Every MUST/SHOULD/MAY below maps to those IDs.

| Area | Normative contract (EN / IT) | Applicable requirement IDs |
|---|---|---|
| Record | Each immutable Approval MUST contain ID/version, project or specification-package ID, exact artifact and dependency hashes, scope (`specification|project|scene|layer|candidate|script|audio|RenderPlan|variant|render`), outcome, actor identity, authority snapshot (credential/key identity, role assignment, issuing authority, policy hash and validity) or policy identity, thresholds/observed values, evidence refs, rationale/comment, created/expiry times and status. Identification MUST NOT be treated as authorization. / Ogni Approval DEVE includere project o specification-package ID, scope e snapshot di autorità; identità NON equivale ad autorizzazione. | APPROVAL-001 |
| Outcomes and roles | Outcomes MUST be `approve|reject|request-changes|waive-validation`; roles are `creator|reviewer|owner|legal|language-reviewer`. Reject/request-changes/Waiver MUST include rationale. Policy MUST enforce separation of duties; creator self-approval MAY cover internal creative work but MUST NOT cover required consent, rights, Waiver or final release. / Esiti e ruoli DEVONO essere quelli elencati; reject/request-changes/Waiver DEVONO avere rationale. La policy DEVE imporre separazione; auto-approval creator PUÒ coprire lavoro creativo interno ma NON consenso, diritti, Waiver o release finale richiesti. | APPROVAL-001–APPROVAL-003 |
| Policies | `manual` waits; `auto` creates Approval only after versioned Validation thresholds pass; `skip` creates no checkpoint; `on-failure` opens review on configured failure/cost/degradation. Required `unknown|error|missing|not-evaluated` MUST count as failure for checkpoint evaluation. Every transition MUST record policy/evidence/threshold hashes; policy change MUST NOT rewrite history or convert failure to pass. / Unknown/error/missing required DEVONO attivare failure; la policy NON DEVE riscrivere storia o convertire fail in pass. | APPROVAL-001, APPROVAL-002 |
| Expiry and supersession | Approval MUST become superseded when artifact/dependency hash changes. Its historical record MUST remain immutable; current validity MUST be re-derived at use time from Approval, authority/policy, Claim, Quote/licence and Rights/Consent revocation/expiry, using the earliest applicable bound. / Lo storico resta immutabile; validità corrente DEVE essere ricalcolata da tutte le dipendenze. | APPROVAL-001, APPROVAL-004 |
| Batch | A batch MUST display a closed, enumerated set before confirmation and MUST create one record per exact hash; it MUST NOT approve future/dynamic members. / Un batch DEVE mostrare un insieme chiuso enumerato e creare un record per hash; NON DEVE approvare membri futuri/dinamici. | APPROVAL-001 |
| Waiver | A Waiver MUST retain the failed Validation, authorized actor, scope, rationale and expiry. Missing likeness/voice-cloning consent, mandatory use rights, corrupt/unrenderable bytes, approved-hash mismatch, impossible required output, prohibited content, missing required legal/CTA/caption, and blocking unverified Claim MUST NOT be waived. Budget failure requires budget change, not Waiver. / Il Waiver DEVE conservare failure, autorità, scope, rationale e scadenza. La lista indicata NON DEVE essere derogabile; budget insufficiente richiede modifica Budget. | APPROVAL-002, APPROVAL-003, RIGHTS-003 |
| Selection and variants | Candidate Selection MUST remain separate. Master Approval MAY be inherited only when variant artifact and Validation hashes are identical; crop/layout/translation/audio/caption/CTA changes require variant-specific decision or valid auto-policy. / Candidate Selection DEVE restare separata. Approval master PUÒ ereditarsi solo con hash artefatto/Validation identici; le modifiche indicate richiedono decisione variante. | APPROVAL-001, APPROVAL-002 |
| Revocation/rollback | Revocation MUST append actor/cause/time, mark dependents stale/blocked and preserve old renders as auditable but non-publishable. Rollback MUST create a new revision based on an old version and MUST NOT rewrite intervening events/decisions. / Revoca e rollback DEVONO essere append-only/non distruttivi come descritto. | APPROVAL-004, RELEASE-005 |

Decision bundles imported from another machine MUST be idempotent and bind bundle/project/decision IDs, artifact/dependency/policy/authority hashes, creation/expiry and replay protection. An unsigned or unverifiable local bundle MAY be retained as `untrusted` evidence but MUST NOT authorize legal, consent, rights, Waiver or final-release decisions.
